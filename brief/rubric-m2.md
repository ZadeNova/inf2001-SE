## Appendix C. Design and Prototype for Milestone 2 (2nd half)

For Milestone 2, each team needs to submit a Milestone 2 Report and make a group presentation in Week 12. The Milestone 2 Report should follow the provided report template, which serves as a guide for the required structure and content.

### B.1 Requirements for Milestone 2 Report (20%)

#### B.1.1 Content (15%)

The Milestone 2 Report should include a chapter for each of the items as below.

- Introduction
  - Cover page
  - Team members, role and their contributions
  - Plagiarism declarations
  - Elaborations on AI usage and declarations with changes made on the AI outputs (if available)
  - Description of updates from M1 (if any)
  - Summary of final features /use cases that are tied to the wireframe
  - Final Class diagram
- Component Diagram (3%)
- Detailed Design (5%)
  - Architectural Pattern
  - Design Pattern
- Testing (4%)
  - Black-box Testing
  - White-box Testing
- Wireframe (3%)
  - screenshot and description

#### B.1.2 Presentation (5%)

##### B.1.2.1 Formatting (2%)

- Professionally structured report, clear language, good formatting, references where needed.
- All artifacts align (e.g., requirements ↔ use cases ↔ design ↔ prototype).
- Terminology consistent throughout.
- No contradictions.

##### B.1.2.2 Group Presentation (3%)

- The presentation slides or demo should cover focus on presenting the prototype wireframe
- The team can choose the number of presenting members and it is not compulsory to have the whole team to make the presentation.
- Logistics information, e.g., presentation date and time, will be shared later.

### B.2 Submissions

- Each team only needs to submit one zipped file including the Milestone 2 Report and the presentation slides.
- The zipped file should be named as: INF2001-M2-Team X.zip. For example, Team P1-1 should name the zipped file as: INF2001-M2-P1-1.zip.
- The deadline for submission is: **11:59PM, 20 Nov 2026 (Friday)**.

A penalty of **20%** per day for each deliverable will be imposed for late submission unless extension has been granted **prior** to the submission date. Request for extension will be granted on a case-by-case basis. Any work submitted more than 4 days after the submission date will not be accepted and no mark will be awarded.

### B.3 Peer Evaluation

All students need to complete their peer evaluation by **11:59PM, 20 Nov 2026 (Friday)**. If not, there will be a **10% penalty** for your own peer evaluation mark and the contribution credits will be evenly distributed among the other team members.

### B.4 Rubrics

#### Component Diagram (3%)

| Item | Criteria |
|---|---|
| Component Diagram | • The component diagram should be complete, logically correct, and use appropriate UML 2.5 notation.<br>• The component diagram must be consistent with the final class diagram and adequately support the identified user requirements/use cases.<br>• The diagram must be accompanied by a clear description of the responsibilities of the major components and their interactions/interfaces.<br>• Dependencies and interfaces between components should be clearly and correctly represented. |

#### Detailed Design (5%)

| Item | Criteria |
|---|---|
| Architectural Pattern | • An appropriate architectural pattern is selected and correctly applied to the system.<br>• A clear rationale is provided explaining why the selected architectural pattern is suitable for the system and its requirements. The discussion should identify the main responsibilities of the architectural elements/layers<br>• A supporting diagram illustrating the application of the selected architectural pattern must be provided.<br>• The supporting diagram must be consistent with the final class and component diagrams and clearly illustrate the relevant interactions or dependencies between system elements. |
| Design pattern | • ONE (1) suitable design pattern that addresses an identified design problem in the system is selected and supported by a clear rationale. The explanation should describe the design problem addressed by the pattern and how the pattern improves the proposed design.<br>• A relevant excerpt of the class diagram must be provided to illustrate how the selected design pattern is implemented.<br>• The diagram must be consistent with the final class diagram and clearly identify the roles/classes participating in the design pattern. |

#### Testing (4%)

| Item | Criteria |
|---|---|
| Blackbox Testing | • A clear description of the selected function/method and its expected behaviour is provided.<br>• The description must be supported by a complete decision table that includes causes, effect, and combination, together with a reduced table (if it applies)<br>• Test cases must be systematically derived from the final decision table, with clear inputs, expected outputs, and traceability between each rule and its corresponding test case(s).<br>• The selected function/method should contain sufficient conditional logic to demonstrate meaningful application of decision-table testing. |
| Whitebox Testing | • A clear description of the selected method is provided. The selected method should contain sufficient control-flow complexity to allow meaningful white-box testing.<br>• The analysis must include the method's pseudocode, a corresponding Control Flow Graph (CFG), and a correct calculation of cyclomatic complexity.<br>• The selected method should result in a CFG containing at least eight nodes and two decision points. |

#### Wireframe (3%)

| Item | Criteria |
|---|---|
| Wireframe | • The final wireframe must provide adequate coverage of the identified user requirements and use cases.<br>• Wireframe shows good design, functionality and user centered focus<br>• Each relevant wireframe screenshot should be accompanied by a concise description and clearly mapped to the corresponding use case(s). |

#### Presentation (5%)

| Item | Criteria |
|---|---|
| Formatting | • Professionally structured report following the required template, with clear headings, numbering, captions, figures/tables, references where needed, and consistent formatting throughout.<br>• Clear and grammatically correct language, with consistent terminology across all sections and artefacts.<br>• Strong alignment and traceability across requirements, use cases, final class diagram, component diagram, detailed design, testing artefacts, and prototype wireframes.<br>• No major contradictions, inconsistent naming, missing labels, or presentation issues that affect readability or understanding. |
| Group Presentation | • Presentation focuses on the final prototype wireframe/demo and clearly explains how it supports the identified requirements and use cases.<br>• Key user flows are presented clearly, showing how users interact with the proposed system.<br>• Prototype is well aligned with the report artefacts, including requirements, use cases, design, and testing where relevant.<br>• Demo is clear, professional, well organised, and delivered within the allocated time.<br>• Team can justify design decisions and respond to questions or requests to elaborate on selected parts of the project. |
